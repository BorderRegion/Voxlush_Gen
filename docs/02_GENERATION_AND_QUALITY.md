# 02 · 模型独立创作、弱模型适配、适量质检与主题覆盖

## 1. 先降低单次推理负担，不降低建筑表达能力

需要解决的是模型在长程序、复杂空间和反复修改中的可靠性，不是将建筑改成有限模板。低层绘图 API、坐标/材料规则应简短、准确且完全一致；代码允许本栋自由函数和循环。不给所有任务一个整栋示例，不把示例建筑作为所有输出的隐性骨架。

作者输入固定四块：任务/场地要求；完整但精简的原语与材料合约；本阶段输出格式；必要的当前证据。通常不传全局历史、多篇评审或完整失败链。系统提示放稳定前缀，利于支持缓存的端点复用；不能假定所有池都支持缓存或编造命中率。

坐标、方向、材料和组件必须来自版本化 runtime contract。特别保留旧问题的正确说明：门洞 standing entry 在楼板顶面 +1；W 的 wall_id 是已存在墙体 owner；开洞坐标和深度必须匹配实际墙体；后绘制结构不能重新填回开口。具体原语参数从真实运行时抽取/同步并测试，不继续用字符串截断生成残缺提示。

程序可附 `DESIGN_INTENT`、`DESCRIPTION_ZH/EN`、`DECLARED_TAGS` 等短字面量；这些只是模型声明，不能自动成为 observed。双语描述尽量同一次作者/终稿调用完成，不为每栋额外收费翻译。

## 2. 两条执行路径已经确定

### 2.1 直接路径：简单至中等复杂度

```text
brief → 作者写完整本栋源码 → 执行/几何 → 真实渲染 → 一次视觉审核 → 归档
```

作者在同一调用中给简短意图和完整程序，不要求先写长计划。适合小中型单体、简单公共设施、自然地景片段等；具体分流用先导结果验证，不按主题名字粗暴判断。

### 2.2 两阶段路径：长代码或复杂空间

```text
brief → 作者写本栋自由骨架 → 执行/骨架检查
      → 同一栋自由精细化 → 执行/最终几何 → 渲染 → 一次视觉审核 → 归档
```

骨架由模型自由设计楼层、体量、通路、庭院、连接、地形或地景关系，不是程序提供的房型。骨架检查只验证已要求的空间关系，不要求最终家具、材质装饰或窗数；骨架通过不能记 accepted。

精细化不应删除有效体量和主要功能来“减少错误”。允许模型修改自己最初不合理的方案，但须记录变更并重新检查受影响的合同。可以在本栋内用函数分块，不把全部建筑切成同样的四翼八房。

默认两阶段适用于旧大型木屋、多层多房/多体量建筑、聚落、洞穴地表复合场景等。没有性能证据前，禁止为全部样本增加第三次“专业规划师”调用；也禁止为了减少调用把所有复杂任务改成小房子。

### 2.3 分流应能学到工程事实，但不引入学习路由系统

首版用可解释规则：请求的可使用楼层/空间关系、预计代码长度、主题在相同模型上的近期失败根因。先导比较直接与两阶段；按 task class 固化简单路由表。模型变更时重新做小型 canary，而不是训练一个复杂路由模型。

路由选择、原因、配置版本写入样本。不能在难任务失败后悄悄重标简单任务充数；改规格需要新任务和明确 lineage。

## 3. 输出与修复格式要适合能力偏弱的模型

### 3.1 作者格式

优先源码文本或单一 Python code fence，避免把长代码塞进巨大 JSON 字符串让模型处理反斜杠。只允许确定性的 fence/换行规范化；不模糊搜索并执行回答中任意一段“看起来像代码”的内容。

完整语义终止、可解析源码、必要入口与元数据是不同检查。解析通过不能证明流完整；文件头刚好是一段合法 Python 的截断仍然不能执行。

源码长度和请求上下文需要留空间给输出/修复。若实际接口没有可靠 token 计数，记录估计与误差，不假造精确值。不要硬性要求上万行代码或固定组件数。

### 3.2 修复反馈

一次只处理 1–3 个同因问题，依赖优先级为：格式/运行 → 坐标/材料 → 必须的空间关系 → 细节 → 视觉。完整错误报告留盘，发给模型的是 root cause、真实坐标/组件、必要源码与上次修复失败的短说明。

小程序优先返回完整修正版，减少补丁协议负担；大程序优先 hash 校验的函数/组件范围替换或已有精确补丁机制。不要首版开发通用 AST 重构引擎。所有补丁必须匹配当前 source_hash，唯一定位；不做不受控模糊替换。定位失败可在剩余预算内降级为一次完整源码修正，不能把格式修复独立无限收费。

`best` 选择先看硬合同/功能保留，再看根因是否解决，再看成本；不能仅以错误数下降为最好。重命名/删除房间、减少任务要求、改变室内为室外、删除复杂结构不应被计作成功修复。

同一根因连续两次无实质进展时终止当前策略，或在已配置/批准的预算内用一次较强模型替代后续修复；不是继续给弱模型整段重写几十次。失败留证据，系统继续其他任务。

## 4. 质量合同按场景分层，而不是按“审查次数”分层

### 4.1 共同底线：每个候选都跑，程序化完成

最终工件可加载、坐标/轴/范围正确、材料与 block state 合法、component_id 完整引用、无重复坐标、无越界/无意义空输出、源码能在隔离环境复现、没有超出资源上限。纯标量/数组检查一次完成；几何统计从同一次构建结果派生，不重新执行源码几次。

有效原语允许的形状都应可表达。不能设置一个对自然岩体不合理的全局“实心比例上限”，也不能用窗数/家具数判断所有场景完成度。

### 4.2 场景质量合同

| 合同 | 必查内容 | 不应套用的要求 |
|---|---|---|
| inhabited | 声明的可用楼层/空间实际存在；入口、通路、楼梯净空按运行时规则可达；开口与墙体一致 | 不强制所有住宅八房、一百组件或相同屋顶 |
| exterior | 主体完整、任务要求的外部结构、材料/开口逻辑；明确标注外观用途 | 不冒充完整室内资产，不把失败 inhabited 改标后直接接受 |
| ruin | 残存体量、可见年代/损毁意图与语义相符；任务要求的可通行处真实可用 | 不把刻意断墙/破顶一律当完整住宅失败 |
| landscape | 地形/水/植被/洞穴实际几何；任务声明的地表/洞内关系；边界与材料合法 | 不要求单连通块、家具、屋顶、房间；合理悬浮奇幻景观按主题处理 |
| mixed | 对分区/对象应用对应合同，再检查任务要求的相互关系 | 不把所有分区当房间，也不自动免除聚落中的室内要求 |
| legacy_large_wooden_v1 | 完整保留旧大型木屋的专用硬规则与约定 | 不推广为所有主题的规则，不降低旧合同 |

任务创建时确定合同和 `interior_requirement`，不是失败后挑最容易通过的合同。混合场景可以在 metadata 中列 region/object scope，其作用是定位检查，不是约束设计几何的 DSL。

`component.category` 应版本化扩展到建筑、地表、岩体、水体、植被、洞内结构、基础设施等；不能把树和岩壁都硬标成 furniture。已有 category 映射保留；增加新类别时测试旧导出兼容。

空间描述不能代替体素证据。支持合理的不规则房间/非矩形通路，不能为了旧 bbox 检查器强迫所有房间矩形。首版可用受约束的体素区域/空间 mask 与 component 关联，不必发明完整 CAD 拓扑系统。

### 4.3 一次实际图像审核

最终体素落盘后渲染两张互补视角，固定风格/光照/材质版本并组合成 contact sheet；复杂遮挡、室内关键通路或洞穴可有目的地增加顶视/剖面。不做与模型输入无关的重复渲染，不用生成式美化图替代实际工件。

同一次图像调用返回 pass / borderline / reject、简短依据、可见缺陷和有限 observed 标签。建议维度：整体体量/轮廓、比例与层次、材料统一与对比、细节逻辑、主题完成度、明显视觉错误。初始 0–4 级评分仅是辅助；不允许平均分掩盖明显缺陷。用校准结果确定 pass 的实际 rubric，记录 rubric_version。

图像检查是另一个上下文中的审核，不等于统计独立的“专家共识”。禁止作者自报美观即通过；也不需要每栋安排三个模型讨论。每个最终 pass 的证据必须包含 input voxel hash、image hashes、评审角色/版本与结果。

borderline：在预算内最多一次针对性补视角/复审或视觉修复；仍不清楚则留待少量人工审核/最终排除。不要因为不确定就永远占用生成队列，也不要把不确定当 pass。

没有已证明能读图的端点：候选进入 `awaiting_review/awaiting_visual`，不计 accepted；队列达到上限后背压。能力 canary 使用少量显然不同的真实图像，并检查回答确实依赖图像；“HTTP 接受了 image 字段”不是能力证明。

### 4.4 抽样与计算复用

几何检查、渲染、评审缓存 key 至少包括 voxel/source hash（按对应任务）、runtime/validator/renderer/rubric 版本与任务质量合同 hash。正文描述改变不等于体素改变；但审评问题改变不能复用旧 rubric 分数。最终 accept 必须使用当前匹配证据。

不设计复杂细粒度依赖图，首版以阶段工件 hash 缓存即可。正确性不足时宁可执行一次廉价完整检查，不把省几十毫秒变成一套无法维护的增量验证系统。

初次可用 60–100 个跨主题输出做一次人工盲评校准；校准期间不是让用户反复修改建筑。生产保留可导出的分层随机抽检包（例如每个 release 的 0.5%–1%，每次不超过 100，按风险调整）。日常流水线不等待每栋人工点击；经确认的缺陷反馈只触发相关 theme/route/rubric 的检查，不重审十万条全部数据。

## 5. 主题系统：256 个种子只是起点

`themes/catalog.json` 包含 32 个家族，每个家族 8 个具体创作种子。编码字段是稳定 ID；中文名称与 focus 是创作任务素材，不声称真实历史建筑学分类或保证文化准确性。

场景组成初始建议：architecture 60%、natural 25%、hybrid 15%。这是可修改的数据集配方；用户选择专门木屋/遗迹活动时只对所选范围计算比例，不强制填其他场景。不要将面向所有主题的配方混进旧集合。

各种子提供建议用途/挑战、合同、规模与环境线索，但模型决定平面、屋顶、形体和细部。`suggested_scale` 不是不可变 bbox；真正 task 中有明确体积/资源边界，仍在 256³ 整数域内。

### 5.1 至少覆盖的维度

用途/功能、建筑或地景家族、气候/场地、材料语言、尺度、空间组织、垂直层次、完好/损毁状态、可进入性、风格/叙事。自然场景额外关注地表—地下、水陆、植被密度与局部生态关系。不是所有维度都必须每次填满，也不做笛卡尔积穷举。

scale 可以分 S/M/L/XL；示意水平 span 约 16–40、40–80、80–144、144–224，在留出边界/屋檐的 256 域内自由选。它们只是任务抽样档位，不能把复杂作品等比例缩放来扩量。XL 未通过资源 canary 时标注待资格验证，不能用 S 冒充 XL。

不能只改变摄影角度、时间、标题或材质就算新建筑。新的主题实例至少在主要体量/空间关系/功能组织等方面存在独立设计意图，最终仍用几何/图像近重复检测验证。

### 5.2 分层采样，按 accepted 补缺口

先采样 scene_type，再选目标份额不足的 family/seed，最后选尚欠缺的场地/尺度/空间特征。种子存在时可以廉价生成基本任务草稿；作者仍独立设计代码。

维护 `target/accepted/active/rejected/duplicate`，调度选择用 `remaining = max(0, target - accepted - 合理预计在途贡献)`，但最终报表只以 accepted 抵扣目标。不能把规划的 active 当最终覆盖。难主题要有最小探索份额（初值约 10% 调用预算）与每类上限，不可因低通过率永远不生成，也不无限投入无效任务。

每个主题正常失效只是普通 rejected；在一个已结清的滚动窗口中，同类完成 24 次有效作者尝试仍无 qualified outcome，暂停该 theme×route 配置并记原因。为了避免视觉队列暂时积压误报零产出，应分几何产出与联合产出观察，并等待对应队列结清。全局生产已经预热、48 个相关候选均已结清且零 accepted 时停止扩量并诊断，不能继续无限花费。这些是先导可调整的止损规则，不是对所有模型的统计结论。

暂缓的主题可以在端点/提示/rubric 变更或预先允许的少量探针后重新获得资格；不要每分钟重试。其他健康主题继续，但面板必须展示 coverage_debt，不悄悄改掉目标配方。

### 5.3 批量扩展创作任务，而不是批量套用几何

支持可选 `brief_expander`：每次约 16 条，相当于一小批创作任务说明；输入已覆盖主题与缺口、避免的重复意象，输出无源码的独立 brief。一次 schema/去重检查，坏的条目丢弃或最多整批修一次，不给每条 brief 再配一个审核模型。

expanded brief 记录来源/模型/batch_id，局部生成任务仍可在 expander 不可用时继续，因此不能把“主题生成代理”变成整个系统单点阻塞。可以用 catalog 的独立种子与少量兼容维度生成基础任务，不需要额外 LLM 才能开始。

扩展器可以提出新家族/新种子，先记 experimental 并做少量 canary，不直接自动修改全局质量合同或允许材料。不声称 256 个种子已经覆盖所有文化/用途，更不把“随机加很多标签”当覆盖。

## 6. 去重：廉价逐级筛选，不两两比较十万条

第一层：实际体素的精确内容 hash，包含实际 block states；这是确切重复，不依赖标题。

第二层：平移归一、多分辨率占用/材料统计、固定视角 perceptual hash、主要结构尺寸形成廉价近重复指纹。水平旋转/镜像可帮助检索候选，但要同时处理方块朝向；不能错误旋转 block state 后直接宣布相同。组内比较、LSH/桶检索和少量 top-k 即可，禁止全量 O(N²) 比较。

近似相同只标 candidate，结合几何重叠/多视角证据确认；不能仅凭同样的木屋外观、组件数或函数名就删独立资产。无法自动确认的高风险组进入小型待审核/从主集暂排除，不每个样本再调用一个去重 LLM。昂贵图像 embedding 不是首版必需，只有廉价指纹明显失效并有证据才引入。

`theme_family_id` 和 `lineage_group_id` 不是同一个概念。所有图书馆属于同一主题家族，但不应全被当同一训练切分组；同一源码衍生、旋转改色、近重复几何才形成 lineage/duplicate 组。

## 7. 防止“数值好看、训练无用”

不能把请求标签直接抄进 observed。`sampling_tags`（抽样条件）、`requested_tags`（任务要求）、`generator_declared`（作者声明）、`observed_tags`（程序/图像/人工证据）、`quality`（检查结果）、`provenance`（来源）分开。

材料、尺寸、组件数、层高等尽量从最终体素统计；风格、空间用途等需注明证据来源，不确定用 unknown。修复后描述/标签要对应当前版本；最终描述不能仍宣称已经删除的庭院。

训练导出优先 instruction→本栋独立 authored source / 原始工具调用，以及可选 instruction→体素或图像条件任务。保留原始提示与最终结果；失败代码不混入正例 SFT。经过验证的修复对单独导出，不能把两个随机不同建筑做成偏好对。

模型不能在训练 target 中看到内部评审答案或未来修复解释。prompt、runtime、材料表与导出 schema 固定版本；潜在衍生家族按组切分，详见数据规范。
