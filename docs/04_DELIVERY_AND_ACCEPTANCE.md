# 04 · Codex 实施顺序、验收、部署与交付

## 1. 执行规则

本文件是最终完成清单，不是要求一直汇报却不开发。按阶段提交可运行代码与结果，正常阶段自动继续。普通实现选择由 Codex 按本包决策，不重复征求用户意见。只有确实缺少不可推断的凭据、预算授权、不可替代数据或不可逆生产操作范围，才集中报告一次。

付费授权缺失时仍完成离线实现、主题、UI、导出与故障注入，不能因为暂时不能实网测试就只交架子；也不能假装实网测试已经通过。代码可运行与模型配置合格是两种不同状态。

## 2. P0：冻结现场与仓库基线

读取目标仓库最新状态，保护已有提交和 LICENSE。查找完整现有工程、已有运行配置和本包 private_inputs，不假定旧压缩包就是全部最新源码。输出一张精简 inventory：入口、依赖、状态写入者、API 链路、数据根、坐标/材料/运行时版本、真实缺失项。

先建立源码、SQLite/旧 state/source/manifest 的备份与 hash 基线；在独立分支开发。旧 patch 用 diff/哈希逐项核对后吸收“修复意图”，不是将 patched/ 无脑覆盖到新架构。原始服务保持原状，除非已有授权明确允许改动。

公开提交只包含筛选后的工程文件。private_inputs 有生产定位信息，只在本地读取。保留上游 license/attribution；不能把第三方代码改标题后当原创。

**验收：**仓库中有可说明来源的基线、依赖锁、数据目录排除规则、最小 README、AGENTS、STATUS；已识别双写 controller 与缺失模块，没有泄露凭据，没有上线改动。

## 3. P1：先贯通本地一条真实链路

实现配置模型、Store、活动/样本/attempt、单 scheduler owner、分资源队列、幂等命令和归档骨架。用一个**真实可执行的小型几何 fixture**走：新任务→执行→几何→真实渲染→文件归档，视觉评审先使用明确的 mock，仅计 fixture，不计生产 accepted。

复用既有底座并修复新任务入口。实现 legacy adapter 和新统一 runtime category 扩展；保留旧木屋合同的回归。独立数据根运行，不写原生产目录。

实现必要 CLI（具体名称可一致调整）：

```text
voxlush --config ... doctor                    # 不收费本地诊断
voxlush --config ... serve                    # API + 单 scheduler + 静态前端
voxlush --config ... campaign create
voxlush --config ... campaign start|drain|pause|resume ID
voxlush --config ... import-legacy --source ... --dry-run
voxlush --config ... export --campaign ID --output ...
voxlush --config ... backup --output ...
voxlush verify-release PATH
```

这些是应实现的产品命令，不应把本包的校验脚本冒充它们。serve 在 allow_live=false 时可以运行 UI 和本地任务；doctor 不自动发“测试连接”的收费推理。

**验收：**空白任务正常进入作者入口；同 source/seed 两次执行 hash 一致；本地真实渲染可读；worker 失败不终止总循环；两个 scheduler 不能争写；原旧失败体素不能因迁移莫名成为 accepted。

## 4. P2：网络、预算与弱模型流程

实现真实 PoolClient adapter、端点能力配置、单层重试、完整流解析、deadline、unknown 状态、全局 cap、延迟重试与预算预留。完成直接/两阶段、简洁反馈、有限修复、实际图像审核接口、版本化质量合同与缓存。

使用本地 fake HTTP/SSE server 注入各种网络行为；fake 只模拟网络，不替代真实几何/渲染模块。将语法/几何失败与运输失败分开，预算计数要可对账。

**验收：**下一节必需故障用例通过；正常路径没有多余规划/反思调用；完整且正确的响应才执行；几何失败没有无消费者的渲染；少量未知请求隔离，不能全局无限卡死，也不能未知费用归零。验证接口不支持某参数时会明确报配置/适配问题，而非反复重试所有任务。

## 5. P3：主题、归档、导出与可用面板

合入 32 家族/256 种子的 catalog，支持场景/家族/规模缺口补齐和可选批量 brief。自然主题真实走一次执行与适用 gate，不仅 UI 下拉框出现 natural。实现目录、canonical arrays、manifest、去重候选检索、按组切分、训练导出与数据卡。

实现四页面和样本详情，连接真实 API/SSE。先用 mock 网络+真实本地工件贯通，再接有授权的真实模型。页面不能有生产 mock fallback，不需要完整交互 3D 编辑器。

**验收：**换主题无需复制 runner；自然场景不套八房规则；旧木屋仍按原合同；反复 export 同一 release 输入得到相同顺序/同计数；下载与 hash 可校验；标签来源区分正确；前端刷新/断网不影响后端；十万行索引列表有界分页。

## 6. P4：模型配置资格与真实小批实验

只有明确预算授权后才进行。优先使用用户已有端点，不擅自推荐/购买新服务，不根据厂商宣传断言能力。一次记录端点读图、可用参数、实际超时与合法容量； canary 随模型/重要提示版本变更再跑，不是每个请求都跑。

### 6.1 试验控制

从跨场景和规模的 16 个代表性 brief 做成对直接/两阶段比较（存在明显无需比较的简单类型可用小型子集，并记录选择）。相同 brief、相同最终质量合同、相同总预算、不同隔离 sample_id；A/B 不互相抄源码。用于调参的样本标 calibration，不作为最终盲测证据。

选定初始路由后，用独立的跨 32 家族任务做 holdout：先 64 个任务验证覆盖和失效类型；再在同一预先批准的总预算内扩到能形成可靠质量校准与稳定性观察的数量。默认先导总候选预算上限建议 300；达上限仍不满足资格则报告模型配置未合格，不无限增样直到数字漂亮。

通过与否用真实图像、几何证据和人工盲审校准，不让生成模型评自己。可安排一次 100 个自动判为 pass 的候选的分层审查（不足 100 时明确不足，不能宣称通过）；这是初次质量定义，不是日常逐栋审核。模型配置尚未获得资格时，它们是 calibration/provisional-pass，不计正式 accepted_unique；资格通过后也不作为盲测样本。人工资源没有给出时准备好可导出盲审包和审核页，不编造人工结果。

### 6.2 预先记录的资格目标

以下是工程初始目标，可以在试验前因任务合同调整并留记录；不能看完结果后偷偷改门槛：

- 任何 confirmed accepted 不允许出现已知硬几何失败、工件 hash 不匹配或伪造视觉来源。
- 100 个分层随机自动判为 pass 的候选 的盲审中，建议至少 96 个符合约定质量；同时报告 n、缺陷类型和 Wilson 区间。小样本率只是估计，不是保证十万条无瑕疵。
- 相同任务组合下，新流程联合产出与视觉水平不劣于可靠性修复后的基线；tokens/accepted 或 accepted/hour 至少有一项有可解释改善。如果成本明显上升，必须有清晰质量收益，不能只说“更完整”。
- 某组基线零 accepted 时，不计算相对费用比；用批准的绝对预算、实际合格数与人工质量结果判断。
- 重试/反思/审核开销应显式分解；一栋无异常简单建筑应该接近 1 作者+1视觉，一栋正常复杂建筑接近 2作者+1视觉。若普遍多出几次调用，查调用图，而不是默认增预算。

样本通过少不能证明 10万级稳定。软件功能即使完成，模型配置没有达到资格，也必须显示 `unqualified_model_profile`，让用户知道瓶颈是能力/预算/质量定义而不是跑不动；不能降低规则骗过交付。

## 7. P5：负载、恢复、部署与发布

### 7.1 离线规模测试（不烧模型费用）

使用 100,000 条 sample 元数据及至少 1,000,000 条压缩/摘要事件或等价可证明压力的 fixtures，验证索引、分页、统计、恢复、导出和内存上界。大型体素只用少量真实样例循环隔离执行，不复制十万份制造磁盘浪费。测试数据必须标 fixture 并在非生产根。

用 fake server 模拟 128/256/512 并发的不同延迟与错误，验证本应用不会越 cap、不会在退避时占槽、不会随任务总量产生无限内存。离线 512 模拟通过不等于真实池支持 512。

性能目标以记录的测试主机为准：100k 索引下常用 overview/分页 p95 建议 <500ms（本机、无网络 RTT、与 scheduler 共同运行）；UI 首屏不下载全库；运行指标聚合不明显拖慢产出，初始目标启用监控前后服务吞吐差异 <5%；差异需要多轮测量，不能由一次快慢当结论。

恢复测试应从待处理索引继续，不对已 finalized 的十万工件做一次全量重构/渲染。测试内存的稳定性与上界，而不只记录某个瞬间 RSS。

### 7.2 真实并发阶梯

在预算和实际许可内逐步 8→16→32→64→更高，达到收益平台就停止；不要求为了交付一定跑到 512。每档留足请求完成和本地排空观察，报告质量组合与队列等待。请求数/观察时间不足时记录 insufficient_data，不编造吞吐。

至少完成一个有授权、有本地积压和恢复观察的真实连续运行窗口（目标约 2 小时，可因预算不足明确报告未满足），并演练一次进程重启后的继续。不能用两小时 sleep 当 soak，也不能把不同负载混合计算性能收益。发布所需证据缺失时明确未完成的验收，不擅自扩大花费。

### 7.3 迁移与发布

import-legacy 先 dry-run、明确总数/冲突/缺失/坐标/标签规则；重复导入不重复接受。旧 complete 但无独立图像审核的样本应保留 `legacy_complete_unverified` 来源，不能悄悄升级当前 accepted。已合格旧资产不覆盖；原始文件保留只读或备份。

切换时 drain 旧服务、备份、停止旧 controller/broker 对样本状态写入、运行一次迁移、验证、启动新唯一 owner，再小批验证。不允许新旧双写“同时跑一晚看看”。

部署用简单 systemd 或已有部署方式；前端构建静态资源，不需要 Node 生产进程。依赖版本与 Python/SQLite/runtime 记录。进程 supervisor 可以有限重启并报警，但不能成为重置预算和请求的手段。

打固定 tag；更新需要 drain、备份、schema 兼容检查、迁移、canary。回滚代码前确认 DB schema 兼容；不兼容则从一致备份恢复并对已产生的新工件做对账，不简单 `git reset` 就宣称回滚成功。

## 8. 必测故障用例（开发/CI 跑，不逐样本重复跑）

| ID | 用例 | 必须观察到的结果 |
|---|---|---|
| T01 | 空白新任务，无旧源码 | 正常新建，不访问 ORIGINAL[sid] 失败 |
| T02 | 磁盘/内存状态不一致的旧复现 | 单一状态已消除旧双写问题 |

## 9. 最终应交付的文件与产品

仓库 README 包含从干净环境安装、配置、启动、目标活动、停止/恢复、导出、备份/回滚的实测命令；命令必须跑过，不引用不存在的模块。配置给脱敏可复制例子与可缺省项。

最小报告集合：

```text
docs/STATUS.md
docs/WORKLOG.md
docs/DECISIONS.md
docs/OPERATIONS.md
reports/acceptance_report.md
reports/model_qualification.json
reports/performance.json
reports/migration_report.json
```

报告列明 commit、环境、运行时/材料/renderer/rubric 版本、真实请求数/预算、接受/拒绝/未知数、失败原因、质量盲评、保留问题。至少一个小型可验证 release/fixture 和一次训练导出；真实资产不足时标注，不伪造新数据。

GitHub CI 跑 lint/typecheck、单测、fake transport、真实小型本地 build/render、schema/export 和 frontend build/关键 E2E；不在公共 CI 里放付费凭据或默认收费测试。大规模/实网测试是显式 job，产出报告并使用独立 data_root。

## 10. 完成定义：四个状态分别声明

1. **Implemented**：要求的真实功能已实现，不是 mock/TODO。
2. **Offline verified**：真实本地底座、网络故障注入、负载与前端测试通过。
3. **Model profile qualified**：预算内的真实模型质量与吞吐资格通过，含实际图像证据及校准。
4. **Deployed**：完成授权生产迁移、固定版本发布、重启恢复与回滚验证。

只有前三项都满足，才能说“生成器与该模型配置已具备规模化运行条件”；还需第四项才能说生产已部署。没有实测模型质量时，不用软件测试通过来代替。发布后正常工作应自动补任务、调度、处理有限失败、归档和更新监控；用户仅在明确的权限/预算/硬故障/模型持续失效时介入。
